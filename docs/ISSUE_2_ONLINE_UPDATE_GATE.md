## 为什么停止发布

真正的 preview.40 助手先把旧 EXE 改名到备份，再把新 EXE 移入原路径，两次操作之间有目标不存在的窗口。测试在第一次改名成功后使助手进程退出（退出码 77），随后实际观察目标仍不存在。**是测试程序重新运行保留的助手，才恢复了原 EXE、配置和数据库。**

机器报告明确包含：

```json
{
  "automatic_without_restarting_helper": false,
  "recovery_helper_restarted_by_test": true,
  "publication_ready": false
}
```

这不影响已验证的正常升级和启动失败自动回滚，但不满足本任务“更新中断后自动恢复”的严格门槛。强杀或断电后，旧版没有自动重启该助手的机制，不能把助手可恢复等同于无人干预可恢复。

首次升级由 preview.40 拷贝自身作为助手执行。仅修改候选 EXE，无法改变候选尚未运行时的旧助手逻辑；贸然发布桥接版也不能声称首跳风险消失。

需要的后续方案是在保留现有更新系统的基础上，验证原子替换/恢复监督等加固，并单独制定、验收 preview.40 首跳的恢复入口或部署前置条件。未解决该条件前不发布，不让用户手动覆盖 EXE 来绕过门槛。

## 用户当前应如何操作

目前 **不能** 直接点击“检查更新”获取本候选；默认清单仍指向原版本。不要更改当前清单地址，不需要下载或执行任何临时脚本。

真实游戏六阶段（编号1绑定、桌面启动、重启复用、ADB恢复、停止/切换保护、1～5五开）均未由本轮 Windows 更新夹具证明通过，仍待满足发布门槛后的实机验收。用户电脑上的 preview.40、配置、SQLite、雷电实例和游戏数据没有被本任务操作。
